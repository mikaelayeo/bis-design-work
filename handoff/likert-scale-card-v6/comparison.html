Card layout prototype — what's faithful, what's prototype-only

The prototype mirrors the real Tooltip and matrix LikertScale architecture where it can — but some patterns are simplified for an HTML/JS sandbox. This page flags which is which so dev knows what to port directly and what to do "the proper React Native way."

Where to copy directly from the prototype

  • Token mapping (every CSS variable maps 1:1 to a SafeTapp theme token — see README).
  • Tooltip architecture: one shared instance, anchor refs, key-based active state.
  • Interaction semantics: combined select+show on info zone, dismiss on backdrop, no timer.
  • Visual structure: card-block layout, info zone tap target, statement number prefix.

Where the prototype takes shortcuts — use the real primitives in code

  • Tooltip rendering: prototype uses inline CSS positioning. The real Tooltip uses a Portal, Animated, and hysteresis-aware side selection.
  • Animation: prototype uses CSS transitions; real component uses Animated.parallel for slide + fade.
  • Re-render on selection: prototype rebuilds the DOM each click. In React Native, state updates re-render only the changed subtree — no DOM rebuild needed.
  • Tap-away handling: prototype attaches a document.click listener; the real Tooltip uses a full-screen Pressable backdrop inside its Portal.

Why these shortcuts were taken

The prototype is a static HTML page — no React Native runtime, no native shadow / elevation, no Animated, no Portal. The simplifications buy a single-file artifact that runs in any browser, but they cost some fidelity in animation polish and edge-case positioning. The intent is for dev to use the real Tooltip component verbatim and only port the visual + interaction decisions from the prototype, not the JavaScript implementation.

Open items for dev to flag back

  • The combined select+show affordance on the info zone — confirm this UX still makes sense once you have it on a device. Specifically: is the 44px tap zone wide enough on small phones, and does the tooltip's "above" placement obscure the question text in any common case?
  • Hysteresis on side selection — the prototype's simple "more space wins" approach can flip if the user scrolls. The real Tooltip's hysteresis prevents this. If dev keeps using the real <Tooltip> directly (recommended), this is already solved.
  • If per-option tooltips become a common pattern, consider promoting tooltipinfo from this folder's types.ts into Forms/Widgets/LikertScale/types.ts so the matrix can opt in too.
