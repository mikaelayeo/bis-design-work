The initiative · why now

Right now, shipping a component is slow

Lots of back-and-forth between design and dev on every component.
Figma ↔ code rarely lands 1:1 — props drift, extra variants creep in.
Accessibility gets retrofitted late, or missed entirely.
The whole system takes a long time to move.
"We want it seamless — a component goes from design to code without the ping-pong, and it's accessible from the first commit."

The process · the principle

Accessibility is built into the component

⌨️

Keyboard

Operable without a mouse — tab, enter, arrows.

🎯

Focus

Visible focus + a sensible focus order.

🗣️

ARIA

Roles, labels, and state for screen readers.

🎨

Contrast

Colors meet WCAG contrast, every state.

"Fix it once in the component → every feature that uses it inherits it. That's why the design system is the right place for accessibility — not a downstream audit."
+ a quick axe / keyboard test per component so it stays accessible as it changes.

Decision · color usage ~10 min

Theme color vs fixed tokens

The rule: use the primary / brand theme only when a slot expresses client identity. Everything meaning-bearing or structural uses a fixed token.

Use primary theme (portal color)Use fixed tokens
Primary button, active tab indicator / text, links, selected & active statesStatus colors (success / error / warning), text, borders, backgrounds, disabled states
⚠️ The deciding constraint = accessibility
  • A client can pick a low-contrast brand color, so theme colors must be contrast-checked (or paired with an auto-derived accessible "on" color).
  • That's why status / meaning never rides on theme — it has to stay legible no matter the portal.
"Tabs call to confirm: active tab = theme; the container, inactive labels, and borders = fixed tokens. Can we agree a short list of slots allowed to use the theme color, and lock everything else?"
