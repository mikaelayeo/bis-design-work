The six ideas that kept coming back 💫

By Day 2 I noticed the same six themes echoing across totally different talks. The pattern was loud enough that I'm treating these as the through-lines for everything below.

🤖

LLM ≠ Agent

Copilot = reactive, prompt-dependent. Agent = goal-oriented, autonomous, has memory. Most "AI features" are copilots dressed up.

💗

Trust > accuracy

In vertical AI, users don't need the smartest answer — they need traceable reasoning, consistent behavior, clear off-ramps.

🪜

PoC ≠ Production

Demos optimize for the showcase. Production has zero failure tolerance and a giant risk surface. The gap eats most AI projects.

👎

Thumbs up/down is theatre

Useless aggregate signal. If a user thumbs-down, what does it mean? Tone? Format? Accuracy? You can't act on it. Design the follow-up instead.

📝

Designers transcribe life

We don't invent workflows. We observe how people already work, transcribe it faithfully, then ask what AI can remove.

🎨

Hire for taste

Every panel said the same thing about new grads: not credentials, not GPAs — creativity, originality, finding what AI can't do yet.

"Treat deployment as the start of learning, not the end of the project." — Ultimarii closing slide. Line of the conference for me.

Fundamentals Production

🤖 What Makes AI Agents Successful

AWS presenters · Amii main stage

The talk that set the tone for two days. Cleanest "LLM vs Agent" definition I've heard in ages.

📍 Quick summary
  • LLM vs Agent: Copilot (reactive, prompt-dependent) vs Autopilot (autonomous, holds memory, orchestrates tools)
  • Real wins: Mayo Clinic — 30% faster diagnostics. Siemens — 20% lower maintenance costs.
  • Why agents aren't shipped everywhere: PoC has wide failure tolerance, production has none + a huge risk surface
  • "Genius with Amnesia" — LLM without memory or proprietary context = production failure
  • BIS lens: most BIS "AI features" are L2 / copilot; Ace + Mia are Level 3 agents — different design problems

What they said

Opened with real customer quotes like "I upload docs to ChatGPT — doesn't that mean I'm using an agent?" Then dropped the framework I'm using forever now:

Copilot · Generative AI
  • Reactive & prompt-dependent
  • Stateless & scripted
  • Waits for instructions
Autopilot · Agentic AI
  • Goal-oriented & autonomous
  • Semantic reasoning
  • Persistent memory
  • Dynamically orchestrates tools

Then the receipts — real enterprise wins:

  • 🏥 Mayo Clinic — 30% faster diagnostics (cross-referencing notes, labs, images)
  • 🏭 Siemens — 20% lower maintenance costs (predictive turbine monitoring)

Then the slide that landed harder than anything else that morning:

"If agentic AI is so great, why isn't it being used everywhere?"

Their answer: "PoC without Flexibility" — demos have wide failure tolerance, production has zero. Then a slide called "Unintended Consequences" — a wall of news headlines:

  • Air Canada chatbot — sold tickets at bad prices, airline got sued 😬
  • Replit's vibe-coding service — deleted a user's production DB and lied about it
  • NYC chatbot — told businesses to break the law
  • McDonald's AI ordering — killed after viral order mix-ups
  • McKinsey chatbot — hacked by another agent in 2 hours

The diagnosis

  • 🧠 "The Genius with Amnesia" — High-IQ LLM + no memory + no proprietary context = production failure
  • 🧩 Anatomy of an Agent — harness + model + memory + tools + data + orchestration. An LLM is one part. Not the whole thing.

Closed with another framework:

Workflow · Level 2
  • Predefined paths
  • Hard-coded logic
  • Fails on errors
Agent · Level 3
  • Dynamic routing
  • LLM-driven reasoning
  • Self-corrects & iterates

What stuck

  • 🔑 Most "AI features" at BIS are L2 or copilot. That's fine — but the design problem is different from Level 3 agent design.
  • 🔑 Ace + Mia are actually Level 3 agents (goal-oriented, dynamic tool use, memory across sessions). The BIS AI summarization feature is a copilot. Different UX language for each.
🎨 Designers 💻 Devs

Bringing it to BIS

  • Use Copilot/Autopilot vocab on the team — stop calling everything "agentic" 🙃
  • Redraw the "PoC vs Prod tolerance" diagram for our internal docs
  • The "Genius with Amnesia" framing = literally why Ace needs the pre-flight skill and Mia reads the codebase before generating. Without that, we're handing devs a brilliant amnesiac.

Questions I'm chasing

  • Which BIS features should graduate from L2 → L3, and which should stay scripted because the risk surface isn't worth the autonomy?
Fundamentals Research

🧠 From LLMs to AI Agents: From Words to Action

Liu Asminov, LLM Builder at OnRamp AI · ATB / TELUS stage

Technical walkthrough of how modern LLMs are actually trained. Way clearer than anything I'd read before.

📍 Quick summary
  • Modern LLMs are trained in 4 stages: Pre-training → SFT → RLHF → RLVR
  • DeepSeek-R1-Zero example: model generates 4 code candidates, an automatic verifier picks the one that runs
  • "By 2030 it'll be 1 month, by 2050 — 1 week" — training cycle compression coming fast
  • BIS lens: my Ace + Mia skill files are basically SFT data. Quality of examples matters more than cleverness of prompts.

What they said

Opened with a contrast — one-shot Q&A (easy, LLM does it alone) vs "solve GitHub issue #104" (hard, needs agent loop, multi-tool calls). The leap between those is the leap from LLM → agent.

Then the modern training pipeline, in one beautiful slide:

  1. Pre-training — predict next token on basically the entire internet. Raw world knowledge gets baked in.
  2. SFT (Supervised Fine-Tuning) — show the model human prompt/response pairs. Teaches it the shape of a good answer.
  3. RLHF — generate 2 completions, humans pick the better one, model learns the preference.
  4. RLVR — newer. Instead of human ranking, a verifier (unit test, math solver) judges. DeepSeek-R1-Zero generates 4 candidate Python fns, picks the one that runs. This is how reasoning models get good at code.

The line I scribbled fast: "by 2030 it'll be 1 month, by 2050 — 1 week." He was talking about training cycle compression. Used the industrial revolution analogy — steam → meat refrigeration → electronics → AI. Each one collapses time faster than the last.

What stuck

  • 💡 I don't need to train a model. But I need to understand why a model behaves the way it does — and that's a function of training.
  • 💡 SFT vs RLHF = different design questions. SFT asks "what does good look like?" RLHF asks "which of these two is better?" The second is what I do in user research every day.
  • 💡 My skill files for Ace and Mia are basically SFT data. Every example I write is a piece of fine-tuning. Quality of examples > cleverness of prompts.
🎨 Designers

Bringing it to BIS

Treat my Ace + Mia skill files like training data, not docs. Every example is SFT. Doing a quality pass on existing skill files with this lens this week. ✨

Questions I'm chasing

  • For BIS AI features that generate text — could we use RLVR with verifiable design-system rules instead of relying on human eval?
  • What does "eval harness" mean for an agent workflow? How would Jobber or Anthropic measure that Ace + Mia are actually producing good packages?

Panel · Day 2

The "why does it work in the demo and not in production" talk. Echoes Day 1's AWS talk but from operators who've been bitten. 🩹

📍 Quick summary
  • Demos optimize for the showcase. Production has zero failure tolerance + huge risk surface
  • The reality gap: scale, messy data, edge cases, latency, cost, failure handling
  • Most internal AI demos have this gap baked in (including some of mine 🙈)
  • BIS lens: define an explicit production-quality bar for Ace + Mia — not "the agent runs," but "80%+ of packages used as-is by a tired dev on a real ticket"

The reality-gap, line by line

  • 📈 Scale — demo handled 5 users; prod needs 500 or 5,000. Behavior changes under load.
  • 🧹 Messy data — demo data was clean. Customer data is not. Performance curve is different.
  • 🦊 Edge cases — the long tail is huge. Model has to handle them or fail safely.
  • ⏱️ Latency — 12 seconds is fine in a demo, unacceptable in prod.
  • 💰 Cost — running an agent per user request adds up fast. Most demos haven't done the math.
  • 🚨 Failure handling — when the agent fails (it will), friendly fallback or 500 page?

What stuck

  • 🙈 Most internal AI demos I've seen (including some of mine) have the demo-to-prod gap baked in. They're sized for the showcase.
  • 🙉 For Ace + Mia: I've been treating "Mia produces a working package" as success. That's the demo state. Production state is: a tired dev on a Tuesday afternoon uses the package as-is 80%+ of the time on a real ticket.
💻 Devs 🤝 Everyone

Bringing it to BIS

Define an explicit production-quality bar for Ace + Mia. Not "the agent runs without error." More like: "80%+ of generated packages are used as-is, no rework needed, by devs on real tickets in real conditions." Measure against this.

Research Fundamentals

🔍 Structured Information Retrieval & Summarization in the Era of LLMs

RBC Borealis researchers · Day 2

Research-flavoured. Not super design-applicable, but the cost/privacy argument matters for regulated industries (= us).

📍 Quick summary
  • LLMs at runtime are expensive, slow, and leak data
  • EBCAR: cross-passage structure encoded into embeddings → 29× faster reranker
  • FACTS: SQL + template logic precomputed per schema → 7× cheaper, privacy-preserving table summarization
  • Thesis: move heavy lifting offline, keep data in-house
  • BIS lens: add to AI feature checklist — "do we need an LLM at runtime, or can we precompute at indexing time?"

What they said

Two systems they presented:

  • ⚡ EBCAR — encodes cross-passage structure into embeddings. Reranker is 29× faster than LLM-based methods at state-of-the-art accuracy.
  • 🔒 FACTS — for table summarization. Generates SQL + template logic once per schema. Runtime needs no LLM call. 7× cheaper, privacy-preserving.

The thesis

  1. LLMs are powerful but costly. Querying at runtime is slow, expensive, leaks data.
  2. Structure in data is a free signal. Cross-passage relations + table schemas can be used directly.
  3. Move heavy lifting offline. Precompute at indexing time. Decouple cost from query volume. Keep data in-house.

What stuck

  • 🛡️ "LLM at runtime is wasteful" is the right framing for BIS. We deal with sensitive training records, compliance data, incident reports — exactly the stuff you don't want sent to a third-party LLM.
💻 Devs 📊 Leadership

Bringing it to BIS

Add to the AI-feature pre-build checklist: "Do we actually need an LLM call at runtime, or can we precompute at indexing time?" Hybrid patterns where the heavy lifting happens at upload-time and runtime is just retrieval are often safer + cheaper.

Questions I'm chasing

  • Which existing BIS AI features could be "precompute at indexing, lightweight at runtime"? Especially the ones touching customer data.
Business Design

⭐ Why Agentic Intelligence Is the Future of AI in the Workforce

Day 2

One of my favorites of Day 2. Maturity ladder from LLMs → workflows → agents → multi-agent. And the talk that made me sit with the question: what's the future of design at BIS? 💭

📍 Quick summary
  • Maturity ladder: LLMs as utilities → automated workflows → agents → multi-agent systems
  • Start with well-defined tedious work. Measure outcomes, not activity. Trust earned in inches.
  • The big question I'm sitting with: what's the future of design at BIS?
  • Working answer: designers move up the stack — specifying intent, setting taste, owning the system that produces design work
  • BIS lens: Ace + Mia are the prototype for what design at BIS becomes — not a side project, the future of the role

The maturity ladder

  1. LLMs as utilities — humans use them ad hoc. Anecdotal savings.
  2. Automated workflows — LLMs embedded in scripted flows. Most "AI features" today live here. Measurable but capped.
  3. AI agents — goal-oriented, autonomous, multi-step. Own outcomes, not tasks. Non-linear savings.
  4. Multi-agent systems — specialized agents handing off to each other. This is the workforce future.

Their tips

  • 🛠️ Start with workflows that are well-defined but tedious. Don't agentify creative/judgment work first.
  • 📈 Measure outcomes, not activity. "Agent did 30 things" = meaningless. "Reduced turnaround on X by Y" = signal.
  • 👥 Design for human-in-the-loop. Agent doesn't replace the human — it reshapes what their job looks like.
  • 🐢 Trust is earned in inches. Expand agent autonomy gradually as evidence builds.

What stuck (the big one)

This talk is the one I haven't stopped thinking about. What is the future of AI for the BIS design team?

Not "what tools will designers use" — that's a small question. The big question is: what becomes the designer's job when agents are doing most of the production work?

My working answer: the designer's job becomes specifying intent, setting taste, and owning the system that produces design work. Less time pushing pixels, more time defining what "good" looks like and making sure the agents converge on it.

Vertical vs Horizontal AI · quick primer (because I didn't know the difference either before this talk):
🌐 Horizontal AI — generalist. ChatGPT, Claude, Gemini. Useful for anyone.
🏔️ Vertical AI — specialized. Deep in one domain. AI for safety training, legal contracts, radiology.

Why their research → production worked (and was hard)

Worked because
  • Research with production constraints from day one
  • Freedom to test task framings
  • Credible pathway from research to product
Hard because
  • Prototype success ≠ operational readiness
  • Users wanted consistency, not novelty
  • Customer environments = messy data + edge cases
  • Commercial = uptime, speed, cost requirements

The four-stage maturity model 🪜

  1. Research prototype — capable, validated at small scale
  2. Pilot workflow — usable, limited controls
  3. Production service — reliable, measured SLAs
  4. Operational system — governed, repeatable outcomes

Each step adds constraints easy to ignore during research. Success criteria shift from "can it work?" to "can we trust and operate it every day?"

  • Traceable reasoning
  • Consistent behavior
  • Clear uncertainty boundaries
  • Outputs that fit existing workflow
Design implications
  • Optimize full decision experience, not benchmarks
  • Expose provenance, confidence, fallbacks
  • Prefer stable behavior over fragile peak performance
  • Design for recoverability when the model is wrong

Closing playbook

  • 📐 Define the decision workflow first, then fit the model
  • 🚪 Create explicit readiness gates for data quality, eval, latency, failure handling
  • 📡 Instrument the pipeline before scale exposes unknown failure modes
  • 🪤 Design for fallback + human review where trust thresholds aren't met
  • 🌱 Treat deployment as the start of learning, not the end of the project.

🔐 Accountable Agents: A Protocol for Trust in Autonomous AI

ACEteam.ai · Day 2

What happens when agents start calling other agents across organizational boundaries. The future shape of agentic systems. 🌍

📍 Quick summary
  • Cross-org agent workflows are coming: consulting firm's agent → research firm's agent → vendor's agent
  • Agents need identity, proof of delegated authority, audit trails — "OAuth, but for agents"
  • Liability gets weird fast when agents take actions you didn't explicitly approve
  • BIS lens: Mia pushing to bis-ship is already a trust boundary. Formalize agent-generated labeling + provenance trail now, not after the lawyers ask.

What they said

As agentic AI moves to production, the next big problem is cross-org agent workflows. A consulting firm's agent calls a research firm's agent calls a vendor's agent. Each is autonomous, each is acting on behalf of someone — and each needs to prove who it is and what authority it has.

It's harder than human identity because:

  • 🤔 Agents make autonomous decisions — "who approved this action" is fuzzier
  • ⚡ Agents talk to agents at machine speed — audit logs have to scale
  • ⚖️ Liability gets weird when an agent takes an action you didn't explicitly approve

Their pitch: a protocol where agents identify themselves, prove delegated authority, and leave verifiable audit trails. OAuth, but for agents.

What stuck

  • 🪞 My Ace + Mia setup is the toy version of this problem. Ace hands off to Mia inside my private repo — fine. But when Mia pushes to bis-ship, that's a different repo, shared with devs. There's a trust boundary being crossed.
  • 🪞 Right now that boundary is implicit (I trust myself, I trust Mia because I review her). At scale, in a real org, it needs to be explicit.

Bringing it to BIS
