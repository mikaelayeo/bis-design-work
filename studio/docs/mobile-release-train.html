Mobile Release Train

Planning & design on the new cadence from Oct 5 Dev & QA start in November: first code freeze Nov 13, first release Nov 27
Why we're changing

One fixed release every four weeks, with a deadline for every discipline

Today mobile releases go out roughly monthly, with no fixed date, no code freeze, and design work arriving whenever it's ready. The new cadence turns that into a release train: a fixed schedule where each discipline knows exactly when its work is due.

A fixed release dateStore submission on the Friday of week 4, every cycle. Everyone, including clients, knows when work ships.
A real code freezeFrom Friday of week 2, only fixes go into the release. QA tests one stable package instead of a moving build.
Known deadlines for design and backendDesign knows when designs must be final; backend knows when APIs are needed. No more guessing what's ready.
Focused meetingsOne short sprint planning that only pulls ready cases, a weekly refinement slot, a retro, and daily bug triage during testing.
Fewer surprises late in the cycleNothing new lands in weeks 3–4 that could break the release. Late cases need a real reason and two approvals.
Room for QA automationTesting everything together at the freeze frees QA time in weeks 1–2 for smoke tests and automation.

What to expect

The first cycles will feel different

  • Early releases may be small. Most current cases need backend work, and cases with new endpoints take two sprints. A light release while the pipeline fills is expected.
  • Missing a deadline means the next train, not a failure. A case that isn't ready at the readiness check, or isn't merged by the freeze, moves to the next release.
  • Week 3 will be bug-heavy. QA no longer tests case by case, so every case's bugs show up together after the freeze. Daily triage keeps it manageable.
  • We'll measure and adjust. Each retro looks at bugs found at the freeze, reverts and late cases, on-time store submission, bugs that escaped to production, and cases carried over.
  • Design will be about one sprint ahead, not two. While October's cases wait on backend, the pipeline fills one sprint at a time.
  • Judge it on cycles two and three. The switchover cycle will be messy by design.

Deadlines and expectations

What each role owns, every cycle

The gate

When is a case ready for sprint planning?

Checked at the week 2 weekly meeting. Only ready cases are pulled at sprint planning. If planning runs over an hour, the cases weren't ready and go back to refinement.

Definition of ready

  1. Written in PM with clear acceptance criteria
  2. Designs final and attached (if it has UI)
  3. Technical review done and blocking questions answered
  4. Estimated
  5. Native change or bisapi change flagged, and sized small or big

Who signs off

Anita · Planning
The case is written and prioritized. Has the final say on what goes in.
Mika · Design
Designs are final and attached.
Dev team
Technical review is done, blocking questions answered, native and bisapi flags set.

Any one of the three can mark a case as not ready.

Rules of the road

How the train runs

  • The code freeze doesn't move.Friday of week 2. Anything not merged by then ships in the following release. The release date moves only for a critical issue.
  • Case cutoff closes the release.End of week 3. Cases with a blocking bug, or that won't be fixed in time, are reverted or removed. It's also the last day to approve a late case.
  • Late cases are the exception.A late case gets in only if there is a real reason it can't wait, it is very low risk, and both the mobile lead and the QA lead approve it, by case cutoff.
  • Backend has a cutoff too.Small cases (new data on existing endpoints) start at the code freeze and must be on staging by release day, the backend cutoff. Big cases (new endpoints) move to the next sprint with their design and hit the same cutoff each sprint until ready. The mobile freeze doesn't apply to backend.
  • Plan two weeks, add stretch.Plan about 2 weeks of dev work per sprint (about 2½ realistically, since weeks 3–4 are shared with release bugs), plus 2–3 ranked stretch cases that meet the same checklist. Unused stretch cases go to the top of the next planning.
  • Merge continuously.Only complete cases merge: code review approved, tested on a real iOS and Android device, /qa-notes attached. Late merges pile bugs into week 3.
  • Dev work order.Release bug fixes first, then committed cases, then stretch cases in rank order, then tech debt and tooling.
  • Ship on the date.Small known bugs don't delay a release. It goes out on Friday of week 4, with an OTA fix the same day or the day after if needed.
  • Release isn't live.Store submission is Friday of week 4. Store review takes about 1–3 days, so users get it early the following week.
  • Design QA replaces per-case checks.With per-case QA gone, Mika reviews the code-freeze build Mon–Wed of week 3, before case cutoff. UI bugs go to daily bug triage.
  • Scope of this cadence.New features and feature improvements. Bug cases and small optimisations can still go into the release package before the final week.

Decided

  • Code freeze is on Friday of week 2, so the India team can finish the week. QA starts testing on Monday.
  • Planning and design switch to the new cadence in October. Dev and QA start officially in November: first code freeze Fri Nov 13, first release Fri Nov 27.
  • Backend splits into small and big cases. Big cases run two sprints, and their designs move with them.
  • Reviews run about three working days, Friday of week 1 to Tuesday of week 2: technical review always, backend and QA design reviews when the case needs them. All feed back into design fixes.
  • Design QA review runs Mon–Wed of week 3 on the code-freeze build.
  • A planning freeze in week 3 locks the design list for the next sprint.
  • Sprints are named by the month they are planned and built, plus the app version: the October sprint is v2.17 and ships Nov 27. "This month's sprint" is the one planned in this month's week 2.
  • Case cutoff (end of week 3) is for reverting or removing cases with blocking bugs, and the deadline to approve late cases (real reason, very low risk, mobile lead and QA lead approval).
  • Backend cutoff is release day (end of week 4). Small backend work starts at the code freeze and must be on staging by then, so mobile gets weeks 1–2 of the next month full time. Big cases hit the same cutoff each sprint; not ready means they move one more sprint.
  • No dev builds in the new process. QA gets the release package at the code freeze; in weeks 1–2 the only other builds are OTA fixes, which QA tests before they go out.
  • Releases go out on the date. Small known bugs ship with an OTA fix the same day or the day after, instead of delaying the release.
  • Meetings: the four weekly meetings each have a purpose (grooming and design check-in, case ready, planning freeze, release check-in). QA joins sprint planning.
  • Capacity: plan about 2 weeks of dev work per sprint (about 2½ realistically) plus stretch cases.

Glossary

Terms used on this page

Code freeze

The cut-off for the release. No new features or improvements go into the release package after it; only fixes. Development continues on the development branch.

Release package

The build cut at code freeze. QA tests it in weeks 3–4 and devs push fixes into it until fix cutoff.

Case cutoff

End of week 3. Cases with a blocking bug, or that won't be fixed in time, are reverted or removed. It's also the deadline to approve a late case: there must be a real reason it can't wait, it must be very low risk, and both the mobile lead and the QA lead must approve it.

Late case

A case that missed the code freeze but is let into the release. Allowed only with a real reason it can't wait, very low risk, and approval from the mobile lead and the QA lead before case cutoff.

Fix cutoff

Mid-week 4. The last fix goes into the release package, then final checks and store submission.

Planning freeze

Week 3 weekly meeting. The list of cases design will work on for the next sprint is locked. Later additions wait a cycle.

OTA

Over-the-air update. A JavaScript-only fix pushed to installed apps without a store release.

Smoke test

A quick pass over the main flows of a build to confirm nothing major is broken. Maestro automation targets these first.

Stretch case

A ready, ranked case beyond the committed scope. Picked up only if committed work is done or blocked.

bisapi

The BIS backend API the app talks to. Cases flag whether they need a bisapi change and whether it's small or big.

Sprint names

A sprint is named by the month it is planned and built, plus its app version: the October sprint (v2.17) is designed by early October, built from mid-October, tested in November and ships Nov 27. Each discipline touches it in a different month, so QA tests the October sprint in November.

This month's sprint

The sprint planned in this month's week 2 and built from week 3. It's the team's shared reference point. Your own focus may be a different sprint: design is already on next month's, and QA is testing last month's.

Template dates

Month 1, 2 and 3 are any three consecutive cycles. Sprints are numbered v1–v6; v3 is the sprint planned in Month 1.

Swimlane timeline

The chart type on the Timeline tab: a Gantt-style timeline split into lanes per discipline, with milestones as markers. It's also called a swimlane Gantt chart.

Staggered sprints

The pattern this cadence follows. Design works one sprint ahead of dev, and QA tests the sprint behind it, so several sprints are in flight at once. Also called dual-track or pipelined sprints.
