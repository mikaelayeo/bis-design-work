Wayfinding
& the Back Button

BIS has back buttons that disagree with each other. Some pages have one, some don't, and some have one that sends you somewhere different than the browser does. This is a starting guideline for deciding which navigation control belongs where — and why "just remove them all" isn't safe yet.

01

Why this exists

This started as a side conversation in a Forms ticket about whether the new Form Builder should have a back button. It turned out to be a much bigger question about how people move through BIS at all.

Sasa Kukuruzovic · PM #16526

"We also don't have consistent back button functionality across the system. If I click through multiple modules, some have back buttons, some don't, some have buttons that don't work… Due to this our users are already used to using the browser's back functionality since they are forced to do it on multiple modules and pages."

Two options were put on the table: add consistent back buttons everywhere, or remove them everywhere and let the browser handle it.

Both are wrong, and for the same reason — they treat "back" as one thing. It isn't. There are at least four distinct jobs hiding under that one word, and each one needs a different control. Choosing between "all" and "none" is choosing between two ways of getting three of the four jobs wrong.

What this document is

A first-pass guideline: the vocabulary, the observed problem, and a decision rule you can apply to a screen in about ten seconds. It is not the final standard — deeper research into SaaS wayfinding patterns is owned separately, and this should be folded into it rather than compete with it.

02

What wayfinding actually is

Wayfinding is the borrowed term from architecture — how people orient themselves in a building without a map. In software it comes down to three questions a user asks, often without noticing they're asking them.

Where am I?
Orientation within the structure of the product. Which module, how deep, what's above me.
Breadcrumbs
How did I get here?
The trail of steps just taken — regardless of where those steps sit in the structure.
Browser history
How do I get out?
Leaving a focused task and returning to the surface it was launched from.
Exit affordance

Three questions, three different mechanisms. The mistake BIS has been making — and it's a very common one — is answering all three with a single button labelled ← Back.

03

The distinction everything hinges on: Back vs. Up

This is the single idea that resolves the whole debate. "Back" and "Up" feel like the same gesture, but they navigate two completely different structures.

  • Back is temporal. It reverses your last step. It follows the trail you personally walked. The browser already does this.
  • Up is hierarchical. It moves to the parent of the thing you're looking at. It follows the product's structure, not your history. The browser cannot do this.

From any given screen these two often land in different places — and both are correct. They're answering different questions.

The rule that falls out of this

Don't build a control that duplicates the browser. Do build the control the browser can't provide. Breadcrumbs aren't a back button — they're the answer to a question the browser was never answering.

04

What we found in BIS: the Online Course case

Walking Online Courses with all three controls available produced three different behaviours from the same screen:

ControlWhere it goes
In-app back buttonBack to the previous view
Browser backThe course list page — regardless of where you actually came from
Mouse side button / shortcutSame as browser back

Two controls a user reads as identical, producing two different results.

This is worse than having no back button at all. A missing control teaches the user nothing false. A control that sometimes agrees with the browser and sometimes doesn't makes backtracking non-deterministic — the user can never build a working model of the system, so they stop trusting all of it.

Why it happens

The browser isn't misbehaving. It's doing exactly what it was told. The problem is that the app never told it anything: if a view doesn't push its own URL, the browser has no history entry for it. Browser back then skips to the last real URL change — which, in this case, is the course list.

Why this blocks "just remove them all"

If we remove the in-app back button from Online Course today, users fall through to browser back — which lands them on the course list no matter where they came from. Removal without fixing routing doesn't neutralise the inconsistency. It hard-codes the wrong destination as the only option.

There's a second consequence that's easy to miss. A view with no URL of its own can't be bookmarked, shared, emailed, or linked from a report. That affects course assignment emails, eCommerce links, and any report that drills through to a course.

And a third, which is the sharpest illustration of the whole problem:

A user with a five-button mouse gets a different result than a user clicking the on-screen button — on the same page, intending the same thing.
05

How other products handle it

Three comparators, and one very consistent lesson: never duplicate an affordance the platform already provides.

The transferable rule

BIS web sits on the same side of that line as Notion web and Toggl: the browser is right there, so we shouldn't be reprinting its buttons. What we're actually missing is the thing both of those products do have and we mostly don't — a nav panel and breadcrumbs strong enough that you always know where you are.

06

The four patterns

Four navigation contexts, four different answers. Almost every screen in BIS is one of these.

Pattern A

Location

The global nav is still visible. The user is somewhere, not doing something. They already have exits — every nav item is one.

No back button. Add breadcrumbs so they know their depth and can climb.

Admin › Courses › WHMIS
Pattern B

Takeover

The global nav is gone. A single focused task — a builder, an editor, a wizard. The app removed every exit, so it owes the user one back.

Exit affordance, labelled by consequence. Never a bare "Back".

←  ·  Cancel  ·  Save & Close
Pattern C

Overlay

A modal, drawer, or side panel. The page underneath is still there — the user hasn't gone anywhere, so nothing should enter browser history.

Close control plus Esc. If browser back closes a modal, the URL is doing something it shouldn't.

✕  ·  Esc
Pattern D

Deep entry

The user arrived from somewhere else entirely — a report drill-through, an assignment email, a notification, a shared link. Breadcrumbs would send them to a parent they've never seen; browser back might take them out of BIS.

A contextual return chip, rendered only when the origin is known.

← Back to Completion Report

Label by consequence, not by direction

This is the detail that quietly causes the most damage. In an editor holding unsaved changes, "Back" doesn't tell the user whether it saves, discards, or asks. Every user has to find out by risking their work.

07

The test

You don't need to memorise the four patterns. You need one question, and the rest follows.

Does this view hide the global navigation?

That's the trigger. Not "is the page deep", not "did it take a lot of clicks to get here". If the view took the exits away, it owes the user one back. If the nav is still on screen, the user already has exits and what they're missing is orientation.

The one-line version

A back or exit control belongs only in views that suppress the global navigation. It returns to the surface the view was opened from, and it is labelled by its consequence — Close, Cancel, or Save & Close — never a bare "Back".

08

Applying it to BIS

Running the test against a few BIS surfaces. These are hypotheses — they need confirming against the live system, and that confirmation is the first piece of real work.

Surface Nav hidden? Pattern What it should get
Form Builder Yes B · Takeover Save & Close + Cancel. Not a back button, and not nothing — a third option neither side of the original debate proposed.
Online Course detail No A · Location Breadcrumbs — and the URL fix. Remove the in-app back only after routing is corrected.
Course player Likely B · Takeover Exit control. Confirm whether progress is at risk on exit.
Report drill-through No A + D Breadcrumbs plus a return chip to the originating report.
SafeTapp (mobile) N/A Different rules No browser chrome exists, so "remove everywhere" cannot apply. Mobile needs its own in-app back, plus correct Android hardware-back handling.

Note the first two rows. Form Builder and Online Course detail have been getting broadly the same treatment, and under this rule they should get opposite treatments. That's a reasonable sign the rule is doing real work rather than just describing what we already do.

What has to happen first

The Online Course finding turns two things from nice-to-haves into prerequisites. Nothing in this guideline can be safely rolled out ahead of them:

  1. Every meaningful view has its own URL. Deep-linkable, bookmarkable, shareable.
  2. Browser back behaves correctly everywhere. Users have already been trained onto it; it is now load-bearing whether we like it or not.
Sequencing

Remove-before-routing makes navigation worse, not better. The audit and the URL fix come before any removal work — including in the new Form Builder.

Open questions

  • On Online Course, does the in-app back return to the actual previous page, or to a fixed parent regardless of origin? Those are different bugs with different fixes.
  • Which modules already push proper URLs, and which don't? This determines whether this is a design-standard job or a routing-architecture job.
  • Does the new Form Builder ship with an interim exit affordance while the standard is being written?
  • Do we hold implementation until the full audit, or fix broken back buttons opportunistically as modules are touched?
Where this goes next

This is a v0.1 starting point, not a finished standard. Deeper research into modern SaaS wayfinding is owned separately — this should feed that work and then be replaced by it. The comparator set here is three products and all of them are consumer or prosumer tools; a deep-hierarchy admin console is the closest analogue to BIS and is the obvious gap.
