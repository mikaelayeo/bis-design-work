Custom Department/Job Label

Lets an admin rename the platform's "Department" field to any custom word (e.g. "Job", "Team", "Site") — with validation, revert, and cross-screen context so the change doesn't get lost.

1Scope

Today, the field used to group users (shown everywhere as "Department") is a fixed, hardcoded word. This feature lets an admin rename it to whatever term fits their organization — "Job," "Team," "Site," etc. — and have that word propagate consistently across the admin settings screen, the user-assignment screen, and shared filter views, without breaking the surrounding sentences or losing track of what the field originally was.

In scope

  • Admin · Edit Label — rename flow on the Training Categories settings screen, tucked behind an "Edit Label" button: opens a modal with the field, 3 inline validation errors, live character counter, save, and revert (with confirmation modal and 2 success toasts).
  • Admin · User Profile Select — when assigning departments/jobs to a user, an info icon + tooltip shows the field's original default label so admins don't lose context after a rename.
  • End User / shared · Training Matrix — the "Filter View" dropdown label reflects the custom name dynamically. This is the only change on this screen.

Out of scope

  • The "Roles | Topics | Departments | Filters" tab/list header on the Training Categories screen. It's a fixed section title, not fed by the custom label value, and stays "Departments" (plural) regardless of what the admin names the field.
  • Any other screen in the platform that references "Department" in copy but isn't listed above — not audited as part of this ticket. See Open questions.

2Key decisions

This spec went through a full copy/UX pass before build. The table below is the paper trail — useful context for dev and QA on why the copy reads the way it does, not just what it says.

DecisionResolution
Edit placeholder"Type alternate label" → "Enter a custom label". "Alternate" was vague; "custom" matches how the feature is described everywhere else.
Empty-field error"Type something to save" → "Please enter a label." Matches the "Please enter…" voice already used elsewhere on this screen.
Too-long error"Label should be less than 20 characters" → "Label must be 20 characters or fewer." "Should" read as a suggestion, not a rule; "less than 20" was ambiguous about whether 20 itself is allowed.
Duplicate-default error"You can't use the default label. Please use another." → "This is already the default label. Choose a different name." Fixed the tone mismatch (contraction + formal clause stitched together).
Sub-field label"[Label] Name:" → "Name:". Drops the label from the string entirely so it can never read wrong, regardless of what word the admin picks.
Default label stays singularThe seed value for the Label field is "Department" / "Job" (singular). The one exception is the tab/list header, which is a static string and always reads "Departments" (plural) — see Scope.
Duplicate "Original Label" indicatorAn early draft showed "Original Label: Departments" twice — once as a badge in the top nav bar, once under the Label field. The top-nav badge was a build mistake and has been removed; the inline one under the field is the single source of truth.
Modal & toast wordingUnified all three (update toast, revert toast, revert confirm) to the same "Label [past-tense verb]" heading pattern, and dropped the redundant "back" from every instance of "revert back to…" (revert already means "go back").
User Profile Select tooltipReuses the exact "Original Label: [default]" phrase from the settings screen, surfaced via an info icon + tooltip next to the field, so admins recognize a renamed field without leaving the page.
Edit Label moved behind a buttonNew this pass. The field is no longer edited inline on the Manage panel. Default state: the panel heading reads "Manage Department" with an "Edit Label" button (pencil icon) in its top-right corner. Clicking it opens an "Edit Label" modal with the field, live counter, Cancel/Save (and Revert, once a custom label already exists). Once a label is customized, the trigger relocates to a small "Label: Jobs" strip with its own "Edit Label" button, positioned above the panel.
"Manage [Label]" panel copy no longer tracks the renameChange, confirmed across both the default and renamed screenshots: the panel heading, its two lines of body copy, and the "Name:" sub-field now always read the system default ("Department") — they do not switch to "Jobs" after a rename. Only the small "Label: Jobs" strip above the panel, the User Profile Select field, and the Training Matrix filter reflect the custom name. This supersedes the earlier "grammar-safe template" decision below, which is no longer load-bearing on this panel (nothing here substitutes the label anymore) — see §8 to confirm this is intentional.
Superseded — grammar-safe body copy templatePreviously: rewrote the panel's body copy so the custom label never carries plural/grammatical weight ("one or more [Label] entries," "each [Label]," "more than one [Label]"), since the label used to be substituted inline and broke for words like "Jobs" ("Jobs Name:", "different Jobs"). Now moot on this panel per the row above — kept here for history since the same principle would apply again if any screen resumes substituting the label into a sentence.

Validation rules

  • Required: non-empty after trim (B-3).
  • Max length: 20 characters (B-4). Confirm with dev whether this is enforced as a hard maxlength on the input (can't type past it) or a soft check on Save — the live counter design assumes the admin can type past 20 and see the count, then gets blocked on Save.
  • Must not exactly match the system default string for this field, case-sensitivity to be confirmed by dev (B-5).
  • Client-side validation should mirror server-side — don't rely on the inline error alone.

Edge cases & migration

  • Backward compatibility: accounts that never customize the label should see "Department" everywhere exactly as they do today — this feature is additive, no migration needed for existing data.
  • Concurrent edits: not covered in current designs — if two admins have the settings page open and one saves a rename, does the other see a stale label until refresh? See Open Questions.
  • Permissions: assume Edit Label is gated behind the same admin permission that already governs department/job management; dev to confirm no new permission is needed.
  • Plural admin-entered labels: no longer a risk on this panel — now that "Manage [Label]" body copy stays static (§2), nothing here substitutes the label into a sentence anymore. Re-check this if any future screen goes back to templating the label into copy.

8Open questions

  • Highest priority: the revert confirmation modal and revert-success toast screenshots on file still show the pre-modal UI (standalone Revert/Edit buttons next to the field, tab renamed to match the custom label, "Manage [Label]" body copy dynamically substituted). That layout has since been superseded by the Edit-Label-modal flow (§2, §4.4). Need fresh screenshots of these two states nested in/after the new modal to confirm B-8–B-10 are still accurate.
  • Confirm "Manage [Label]" heading/body copy staying static (no longer tracking the rename) is an intentional simplification and not an oversight in the newest mockup — it was consistent across both screenshots checked, but it's a real behavior change from the prior pass worth an explicit sign-off.
  • The User Profile Select tooltip is hover-only (via the info icon). Does it also need to fire on keyboard focus, and does this page need a tap-to-reveal fallback for touch/tablet admins? Not yet resolved in design.
  • Does the (i) icon/tooltip on User Profile Select appear only once a label has been customized, or always (with the tooltip just repeating the default when unchanged)? Current design only shows the customized case (B-13).
  • Is "Department" the true universal default across every existing BIS account, or do some tenants already have a different stored default? This affects whether "revert to Department" is always the correct destination copy.
  • Is the 20-character limit enforced as a hard input cap or a soft Save-time check? Affects whether the live counter can ever show a number greater than 20.
  • Concurrent edits: if two admins have the settings page open simultaneously, what happens when one saves a rename? Not covered in current designs.
  • During review, a separate "Manage Departments" panel was spotted elsewhere with older, unrelated copy (pre-dating this ticket's fixes). Is that a different screen/module outside this ticket's scope, or a stale duplicate that should be cleaned up? Needs a decision before dev estimates full reach.
